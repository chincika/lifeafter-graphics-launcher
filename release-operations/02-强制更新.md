# 强制更新发布流程

强制策略来自同一份签名清单，不受普通更新检查频率影响。只覆盖已经内置该机制的现代版，不控制经典版或更早没有入口的客户端。

## 判断规则

- 当前程序版本低于 minimumVersion：需要更新。
- 当前版本与 minimumVersion 完全相同，但 SECURITY_BUILD 低于 minimumBuild：需要更新。
- 当前版本更高，或同版本构建号达标：不强制更新。

minimumBuild 不是独立跨版本比较值。更新程序必须同时设置正确的 `desktop-app/main.js` 中 SECURITY_BUILD，不能只更改远端策略。

当前使用：minimumVersion=2.7.0，minimumBuild=4。同版本替换时递增构建号；发布新版本时按需要调整最低版本。

## 后续版本必须保留的启动检查

每次启动均必须检查签名公告和 GitHub 更新，不能由运行中检查频率设置跳过；有效公告每次启动均要展示，更新通过校验后自动安装。包括 beta 在内的后续版本必须运行完整 `npm test`，`npm run portable` 也会自动执行该测试；不得绕过这些检查发布。

## 发布顺序：不可颠倒

1. 读取远端公告清单，保留现有公告和策略。
2. 实现变更，设置版本/构建号，运行 `npm --prefix desktop-app test`。
3. 构建现代版，做真实便携 EXE 启动及托盘检查；后端有变化时重建后端、经典版并同步 runtime-assets-manifest.json。
4. 计算发行文件 SHA-256，更新 SHA256SUMS.txt。
5. 推送代码；正常发版创建新 tag。同版本替换仅在明确授权时更新对应 tag，绝不强推 master 或其他标签。
6. 先上传/替换目标程序 Release 附件，核对远端 digest 与本地一致，并确保该程序 Release 是 Latest。
7. 最后提高公告清单 sequence，并设置目标最低版本/构建号，签名后上传到 launcher-notices。此数据 Release 不得设为 Latest。
8. 从线上重新下载策略并验证：旧构建需要更新，新构建不需要更新，避免无限循环。

同版本替换附件示例（先按实际目录计算并准备文件）：

```powershell
gh release upload v2.6.1 <新EXE路径> <SHA256SUMS.txt路径> --repo chincika/lifeafter-graphics-launcher --clobber
gh release edit v2.6.1 --repo chincika/lifeafter-graphics-launcher --notes '加入安全更新，修复已知问题' --latest
```

EXE 名称必须保持 `LifeAfter-Graphics-Launcher-2.6.1.exe` 等程序版本命名规则，校验文件保持 SHA256SUMS.txt。经典版未改变时保留原附件及其哈希。

强制策略示例：

```json
"updatePolicy": { "minimumVersion": "2.6.1", "minimumBuild": 3 }
```

策略是全量清单的一部分，不能把这一小段单独签名上传。

## 用户侧行为与边界

低版本/构建号会自动检查、下载目标版本，并限制新增或切换帧率解锁；恢复官方帧率不受限制。更新启动器时不等待游戏退出，也不主动结束游戏进程。不会自动撤销已经生效的游戏补丁。

当前实现限制的是帧率应用，不是禁用整个启动器。普通画质功能、已有游戏进程不受此门禁控制。断网不会凭空得知新策略，但此前缓存的已验证策略仍有效。

旧构建号 2 运行中仍每六小时检查；新构建号 3 每一分钟检查。新机制不能改变旧 EXE 已写死的计时器。

撤销错误策略：在更高 sequence 的清单中移除 updatePolicy，或降低最低要求，再签名上传。不能重新上传较小 sequence 来“回滚”，客户端会拒绝旧清单。离线用户须联网后才会解除缓存门禁。
