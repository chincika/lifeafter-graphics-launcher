## 保管与备份

- 私钥只留在开发者设备，离线备份到加密介质或加密密码库；建议至少两份独立备份。
- 备份该 PEM 文件的原始字节，不截图、不贴到聊天、日志、README 或 GitHub 附件。
- 项目 Git 已忽略 `**/notices-private*.pem`、`release-operations/private/` 和 generated/，但忽略规则不是访问控制；分享整个项目文件夹仍可能带出机密。
- 私钥文件当前由本机文件系统保护，没有额外口令封装；获得其读取权限的人可能签署可信清单，务必保护设备和备份。
- GitHub 账号也要做好双因素认证和令牌权限管理。签名无法阻止私钥泄露或开发者主动发布错误内容。

## 换机恢复

从可信离线备份恢复原文件到新机器的 `%LOCALAPPDATA%\LifeAfterReleaseKeys\notices-private.pem`；不要覆盖仍有效的旧文件，先核对来源。使用现有 sign-notices.js 签署测试清单，在本地用程序公钥验签成功后才能发布。

不要执行 `node desktop-app/sign-notices.js init` 来“恢复”。init 只用于首次生成；重新生成的密钥不会被现有客户端信任。

## 遗失或泄露

遗失：从原始离线备份恢复。没有备份则不能继续签署旧客户端可信的数据，需要完整程序更新换公钥。

泄露：停止常规发布，保护 GitHub 账户和令牌，生成新密钥并通过可信完整发行版更新客户端公钥。远程热清单不能直接替换信任根。旧客户端在更新前仍信任旧密钥，不能宣称已全部撤销。

不要将私钥放进 EXE 或发布脚本源码；只有公钥可以打包。不要把“增加代码混淆”当成密钥泄露的解决办法。
